- **Target framework is `net10.0`, not `net8.0`.** No .NET 8 SDK is available on

  The .NET 10 SDK no longer supports the VSTest bridge for MTP test projects.

## Phase 1 — Data source spike (2026-09-04)

- **Called `GET /api/oauth/usage` live** with the local Claude Code login →
  200 OK. Recorded byte-faithfully as
  `tests/ClaudeStatus.Core.Tests/Fixtures/usage-normal.json`, plus four derived
  fixtures (no scoped window, legacy flat keys only, hostile/unknown shapes, and
  the 429 error body).
- **The schema had drifted badly** from the original spike notes. `docs/data-source.md`
  now documents what the endpoint actually returns, with a drift table. Highlights:
  - `limits[]` entries gained `group` and `is_active`; `scope.model` gained `id`
    and `scope` gained `surface`.
  - Eight new codenamed top-level buckets (`tangelo`, `iguana_necktie`,
    `nimbus_quill`, `cinder_cove`, `amber_ladder`, `juniper_tide`,
    `omelette_promotional`, `seven_day_omelette`) — unreleased placeholders.
    Never enumerate top-level keys.
  - New top-level `spend` object and `member_dashboard_available`.
  - `percent` came back as an **int** while `utilization` was a **float** — parse
    both as `double`.
  - `severity` must stay an open string set, not a closed enum.
- **429 is not what it looks like.** An unauthenticated request returns
  `429 rate_limit_error` with `Retry-After: 1731`, *not* 401. An authenticated
  request from the same IP seconds later returned 200, so the buckets are
  separate. Consequence: never read a 429 as either "we are polling too fast" or
  "the credential is fine".
- **Refresh endpoint researched but deliberately NOT executed** — a refresh
  rotates the token pair and would have invalidated the user's live Claude Code
  login. Confirmed by probe that both `platform.claude.com/v1/oauth/token` and
  `console.anthropic.com/v1/oauth/token` are live and parse a JSON `grant_type`
  (400 `Unsupported grant_type: None` for `{}`). Success-response shape remains
  unverified and is marked as such in the doc.
- **Wrote `docs/security.md` v1**: single-asset threat model (T1–T11), the
  per-OS storage mechanisms, transport rules, and a review checklist.
- Response headers carry `anthropic-organization-id` / `anthropic-workspace-id`.
  Added as threat T10 — never log, never fixture, never put in a bug report.

### Notes for whoever writes the provider (Phase 2)

- `usage-normal.json` has real timestamps, so they are in the past. Tests must
  inject a clock; do not call `DateTimeOffset.UtcNow` in the provider.
- The `nimbus_quill` bucket came back as an *object* while its siblings were
  `null`. Any top-level bucket may be either.

## Phase 2 — Core (2026-09-04)

169 Core tests, **91.4 % line coverage** on hand-written Core code (the
generated `RegexGenerator.g.cs` is excluded; including it drags the raw cobertura
number to 78.9 %, which is an artefact, not a gap).

### What landed

- **Domain**: `UsageWindow`, `UsageSnapshot`, `IndicatorMode`, `ThresholdState`.
- **`UsageResponseParser`**, split out from the provider so parsing is testable
  with no network. Deliberately paranoid, per the Phase 1 drift findings.
- **`ClaudeSubscriptionUsageProvider`**: the HTTP call and failure classification.
- **`FakeUsageProvider`**: 7 scenarios, deterministic under a fixed clock.
- **`UsageMonitor`**: polling, jitter, exponential backoff, `Retry-After`,
  stale re-publish, manual-refresh cooldown, cancellation.
- **`ThresholdEvaluator`**, **`AppSettings`/`JsonConfigStore`**,
  **`Redactor`/`RedactingLoggerProvider`**.

### Design decisions worth remembering

- **Every window on `UsageSnapshot` is nullable.** Given how much the schema has
  already moved, "the source did not tell us" is a normal state. A missing window
  renders as a dash, and `ThresholdEvaluator` reports `Unknown` rather than
  `Normal` — a metric we cannot read must never look calm.
- **`UsageSnapshot` has hand-written equality.** The compiler-generated record
  equality compares `OtherWindows` (an `IReadOnlyDictionary`) by reference, so two
  identical readings compared unequal. Caught by a test asserting the fake
  provider is deterministic. It matters because the app will skip re-rendering the
  tray icon when a poll returns unchanged values.
- **`AccessTokenLease`** wraps the token so the `byte[]` is zeroed on every path,
  including exceptions. Getting a token without it is a code smell.
- **No System.Reactive.** `SnapshotSubject` is ~100 lines and the whole surface
  used is subscribe/publish/unsubscribe. A throwing subscriber is isolated so it
  cannot take down polling.
- **`TimeProvider` everywhere**, with `FakeTimeProvider` in tests — no test sleeps.
- **The 60 s poll floor is enforced in `PollingOptions.Normalized()`**, not just
  in the UI, so a hand-edited config cannot get the user rate limited.
- **A structural test asserts `AppSettings` has no `string` property**, so nobody
  can quietly add a field that could carry a token.

### New accepted weakness

`HttpClient`'s header API takes a `string`, so the token must briefly become one
at the HTTP boundary — there is no byte-oriented path through
`HttpRequestHeaders`. Documented as `docs/security.md` §7.4.

### Packages added

- `AwesomeAssertions` 9.6.0 (Apache-2.0) **replacing FluentAssertions**, which
  moved to a paid Xceed licence at v8. Drop-in; same API.
- `Microsoft.Extensions.TimeProvider.Testing` 10.9.0 (MIT, Microsoft) for
  `FakeTimeProvider`.
- `Microsoft.Testing.Extensions.CodeCoverage` for coverage under MTP.

### Toolchain notes

- Coverage: `dotnet test <proj> -- --coverage --coverage-output-format cobertura`.
- `.editorconfig` needed explicit PascalCase naming rules for `const` and
  `static readonly` fields *before* the private-field rule — the first matching
  rule wins, so without them every constant was flagged for a missing `_` prefix.
- CA1716 is suppressed: it objects to `IUsageMonitor.Stop()` clashing with a VB
  keyword. This is an app, not a VB-consumed library, and the name is fixed by
  `CLAUDE.md` §2.

## Phase 3 — Security (2026-09-04)

226 tests (216 Core + 57 Platform, of which 38 skip on Windows). Core line
coverage **91.6 %**.

### What landed

- **`ISecretStore`** with the three methods from `CLAUDE.md` §2 plus
  `Description` and `IsHardened`. `IsHardened` is the signal that drives the
  Linux "no keyring" warning the spec requires; without it the Config window has
  no way to know it is running on the weaker store.
- **`SecretStoreContractTests`**: 11 cases every store must satisfy, including
  "a stored secret survives a new store instance" and "the returned buffer is the
  caller's to zero". Derived fixtures skip themselves when the mechanism is
  absent, so every CI leg is green and the relevant leg is meaningful.
- **Windows `DpapiSecretStore`** — DPAPI `CurrentUser` + a per-install random
  32-byte entropy file. Verified on this machine.
- **macOS `KeychainSecretStore`** — `Security.framework` P/Invoke.
- **Linux `LibsecretSecretStore`** + **`AesGcmFileSecretStore`** fallback
  (`nonce(12) ‖ tag(16) ‖ ciphertext`, key file `0600`).
- **`CredentialService`**, **`CredentialFormat`**, **`AccessTokenLease`**,
  **`ClaudeCodeFileTokenSource`**, **`StoredTokenSource`**.

### Design decisions worth remembering

- **A failed decrypt returns `null`, never an exception.** A config copied from
  another machine producing "there is no credential here" *is* the designed
  behaviour for threat T6, not an error condition.
- **`CredentialFormat` works on `byte` spans**, never strings, and its messages
  never echo any part of the value. It calls out a pasted *refresh* token
  specifically — that mistake otherwise surfaces as a baffling 429.
- **`ClaudeCodeFileTokenSource` returns null for an already-expired token** rather
  than sending it. Otherwise the user sees a 429 that looks like rate limiting
  when the real answer is "open Claude Code to refresh your login".
- **It wipes the entire file buffer**, not just the access token — the same file
  holds the refresh token, which is the more valuable of the two.
- **A 429 during "Test credential" is `Inconclusive`, never success.** An
  unauthenticated request also returns 429, so calling it a pass would tell a
  user with a broken token that everything is fine.
- **`CredentialService.StoreAsync` zeroes the caller's buffer in a `finally`**,
  including when the token is rejected as malformed.
- **DPAPI entropy uses `FileMode.CreateNew`** so two processes racing on first
  run cannot end up with different entropy and silently invalidate each other.

### Security review

`docs/security.md` is now v2. The §6 checklist was run end-to-end; everything
that can be checked at this stage passes. T5, T6 and T11 move to done. One item
stays open by necessity: the Linux keyring warning cannot be confirmed to render
until Phase 5 builds the Config window.

Verified by grep this round: exactly one HTTP destination in the whole codebase,
no hardcoded key/salt/IV, and no key derived from anything guessable.

### Caveats to carry forward

- **macOS and Linux stores are written to their documented contracts and have
  never executed.** They compile and are covered by the shared contract tests,
  but those tests skip on Windows. Treat the first macOS/Linux CI run as the real
  verification, and expect P/Invoke signature bugs there rather than logic bugs.
- The copied-config tests move ciphertext next to *different* entropy on one box.
  That is a good proxy for "another machine", not a proof. Real cross-machine
  confirmation belongs in the Phase 5 QA checklist.
- `RedactingLoggerProvider` exists and is tested but is not yet registered
  globally — there is no logging pipeline until Phase 5.

### Toolchain notes

- `System.Security.Cryptography.ProtectedData` added (Microsoft, MIT).
  `ProtectedData` is not in the base framework; `CLAUDE.md` §4 names it.
- CA1416 is suppressed **in `tests/` only**. The platform tests deliberately
  reference every store to assert cross-platform invariants and guard at run time
  with `Assert.Skip`, which the analyzer cannot recognise as a guard. Production
  code keeps CA1416 enforced.
- Fixed a flaky test of my own making: `Start_polls_repeatedly_and_Stop_ends_it`
  advanced the fake clock once, racing the loop task's timer registration. It now
  nudges the clock until the condition holds. Confirmed stable over four
  consecutive full runs.

## Phase 4 — Platform services (2026-09-04)

315 tests. 268 run and 47 skip on Windows; the skipped ones run on their own
CI leg.

### What landed

- **`IPlatformInfo`** + `PlatformInfoBase` and three implementations. Supplies
  the config directory, an OS name for the Info window, the executable path for
  autostart, and a `TraySupport` reading.
- **`IAutostart`** three ways: `RegistryAutostart` (HKCU Run key),
  `LaunchAgentAutostart` (LaunchAgent plist), `XdgAutostart` (desktop entry).
  All per-user, so none of them needs elevation.
- **`PlatformServices.AddPlatformServices()`** in `ClaudeStatus.App/Composition` —
  the single place in the codebase that branches on the operating system, per
  `CLAUDE.md` §1.3. Deliberately free of Avalonia types so it is unit testable.
- **`ClaudeCodeCredentials`**, extracted from `ClaudeCodeFileTokenSource` so the
  parsing is shared, plus **`ClaudeCodeKeychainTokenSource`** for macOS.

### Design decisions worth remembering

- **macOS needed its own Claude Code token source.** Claude Code stores its
  credential in the Keychain item `Claude Code-credentials` on macOS, not in
  `.credentials.json`, so the file-based source would have silently found
  nothing there and reported "not logged in" to every mac user. Same JSON,
  different home. `KeychainSecretStore.RetrieveRawAsync` matches on service name
  alone, because the account name is the user's login and unpredictable.
- **`ExecutablePath` prefers `Environment.ProcessPath`.** For a single-file or
  Velopack build that is the real executable; the managed assembly location is
  not, and an autostart entry pointing at the wrong one silently fails to launch.
  It returns null rather than guessing, and `IsSupported` goes false so the
  Config window can disable the checkbox instead of offering a dead switch.
- **The Windows Run value is quoted.** `C:\Program Files\…` is the normal install
  location and an unquoted path with a space is parsed as command plus arguments.
- **The LaunchAgent sets `RunAtLoad` but not `KeepAlive`.** This is a tray app
  the user may legitimately quit; `KeepAlive` would relaunch it against their
  wishes. We also do not shell out to `launchctl load`, which would start the app
  the moment someone ticks a checkbox.
- **The desktop entry escapes backslashes and quotes paths with spaces**, as the
  desktop entry spec requires.
- **Linux `TraySupport` is honest about being a guess.** No display server is the
  only case we can be sure of. A bare GNOME session reports `Unlikely` because
  StatusNotifierItem needs a third-party extension we cannot detect — the app
  still starts and still tries, it just warns.
- **On Linux the store choice is made once, at composition time**, and the
  fallback's `IsHardened = false` is what will drive the Config warning (T11).

### Toolchain notes

- `Microsoft.Win32.Registry` needs no package: it is in the net10.0 reference
  pack. `[SupportedOSPlatform("windows")]` is enough.
- `ClaudeStatus.Platform.Tests` now references `ClaudeStatus.App`, because the
  composition root lives there per `CLAUDE.md` §2. That pulls Avalonia into the
  test project, which is tolerable and keeps the documented architecture.
- xUnit v3 has no `[SkippableFact]`; `Assert.Skip("reason")` is the replacement,
  and `PLAN.md` has been corrected.
- `InternalsVisibleTo` added to the macOS and Linux platform projects so the
  plist and desktop-entry generators can be asserted directly. Their escaping
  rules are the likely failure mode and cannot be driven through the public API
  from a machine of the wrong OS.

### Caveats to carry forward

- **The macOS and Linux autostart implementations have still never executed.**
  Their string generation is tested everywhere; the file writing is tested only
  on the matching CI leg.
- `RegistryAutostart` tests write to the real HKCU Run key and remove the value
  in `Dispose`, including on failure. Verified clean afterwards.

354 tests (307 run, 47 skip on Windows). The app now actually runs: launched in

### What landed

- **Headless lifetime**: `ShutdownMode.OnExplicitShutdown`, no `MainWindow`.
- **Details**, **Config** and **Info** windows, with `ConfigViewModel`,
  `DetailsViewModel`, `UsageBarViewModel` and `InfoViewModel`.
- **`AppServices`**: the full service graph, including the single `HttpClient`
  configured per `docs/security.md` §5 (15 s timeout, no redirects, no proxy).
- **`TrayApplicationController`**: owns the monitor, the indicator and the windows.
- **`docs/qa-checklist.md`**: the manual per-OS pass.
- **New `ClaudeStatus.App.Tests` project**, including headless Avalonia tests.

### Avalonia APIs, verified not guessed

Four of my first guesses were wrong, and the build or the docs caught each:

- `RenderTargetBitmap.Render(visual)` **requires the visual to be attached to a
  visible window**, which this app never has. The right call is
  `CreateDrawingContext()`, which draws offscreen with no window at all.
- The toggle enum is `MenuItemToggleType`, not `NativeMenuItemToggleType`.
- Template icons are `MacOSProperties.SetIsTemplateIcon(trayIcon, bool)`, not a
  static on `TrayIcon`.
- `TextBox.Watermark` and `Window.SystemDecorations` are **obsolete in Avalonia 12**
  — they are now `PlaceholderText` and `WindowDecorations`.
- `Screen` lives in `Avalonia.Platform`, not `Avalonia.Controls`.

The Avalonia docs MCP has no `MacOSProperties` entry, so that one was confirmed by
reflecting over `Avalonia.Controls.dll` directly. Worth remembering as a fallback
when the docs come up empty.

### Design decisions worth remembering

- **The template `ViewLocator` was deleted.** It resolves views by reflection
  (`Type.GetType` + `Activator.CreateInstance`), which will not survive the
  trimmed builds `PLAN.md` Phase 7 asks for. This app has three fixed windows and
  no dynamic view switching, so an explicit `DataTemplate` is both simpler and
  trimming-safe.
- **The tray icon is rendered at 2x and left at 96 DPI**, letting the tray
  downsample. That avoids guessing the scale factor on a HiDPI display.
- **The old bitmap is disposed after the new one is assigned**, not before — the
  backend may still be reading it during the swap. This runs once a minute
  forever, so a leak here would be a slow, real problem.
- **`IsTemplateIcon` is off exactly when the threshold is exceeded.** A macOS
  template icon is drawn as a monochrome mask that follows the menu bar
  appearance, which is what we want normally but would throw away the red.
- **Both view models marshal to the UI thread themselves.** The monitor publishes
  from its poll loop; doing the marshalling in the view models keeps Core free of
  any UI framework.
- **Windows hide rather than close**, so reopening is instant and the details
  view model keeps its subscription.
- **The details window never fetches directly** — it goes through the monitor, so
  it cannot become a second source of traffic to a rate-limited endpoint.
- **A suppressed Refresh says so.** The cooldown exists to stop us getting
  throttled, and a button that silently does nothing looks broken.
- **A failed autostart write does not lose the other settings.** It reports the
  problem, unticks the box, and saves everything else.

### Testing

- **Headless Avalonia tests are the only way to catch a broken AXAML file or an
  unresolvable binding** — both compile cleanly and fail at load. `dotnet build`
  passing is not evidence that a window opens.
- `HeadlessAppFixture` boots one Avalonia session per process on its own STA
  thread; every UI test runs inside it via a collection fixture.

### A test that was misbehaving

`PlatformInfoTests.EnsureConfigDirectory_creates_it_and_is_idempotent` was calling
`EnsureConfigDirectory()` on the **real** platform info, so merely running the
suite created `%APPDATA%\ClaudeStatus` on the developer's machine. It now uses a
throwaway directory and cleans up after itself.

### Caveats to carry forward

- **The tray icon has never been seen by a human.** The automated tests prove a
  bitmap of the right size comes out; they say nothing about whether it is legible
  at 16 px, whether the red is visible on a light tray, or whether the ring looks
  right. `docs/qa-checklist.md` §2, §3 and §8 exist for exactly this.
- **`PositionNearTray` is an approximation.** Avalonia exposes no tray-icon
  position, so the details window goes to the corner of the primary screen's
  working area where the tray usually is. Wrong for a top or left taskbar, and
  wrong on a multi-monitor setup where the tray is not on the primary screen.
  Worth revisiting if it annoys anyone.
- **macOS and Linux UI behaviour is still unverified**, as with every phase since
  Phase 3.

## Phase 6 — Hardening (2026-09-04)

379 tests (332 run, 47 skip on Windows). Three of the four items are done; the
fourth was measured and **fails its target** — see below.

### What landed

- **`ISnapshotCache` / `JsonSnapshotCache`**: the last good reading is cached
  beside the settings file, and the monitor is seeded from it before the first
  poll. The tray is populated instantly on launch, and stays populated offline.
- **`IndicatorAlert`**: a missing or rejected credential draws a red `!` and a
  left click opens Config instead of the details window.
- **`SingleInstanceGuard`**: an exclusively-opened lock file stops autostart plus
  a manual launch producing two tray icons.

### Design decisions worth remembering

- **The cache uses a flat DTO, not a serialised `UsageSnapshot`.** The domain type
  will change shape; the file on disk must degrade to "no cache" rather than
  crash the next launch.
- **A cached reading is always marked stale**, because by definition it was
  fetched before this process existed.
- **A cache older than two days is ignored.** A week-old percentage is not
  information, it is a misleading number in a tray.
- **Only fresh readings are cached.** Re-saving a stale one on every failed poll
  would keep resetting its age and defeat the staleness cap entirely.
- **Only a credential problem raises the alert.** A network failure or a 429
  resolves itself, so it must not nag — and a 429 proves nothing about the
  credential anyway.
- **The single-instance guard is a lock file, not a named `Mutex`.** Named mutexes
  behave differently across the three platforms (on Unix .NET maps them onto named
  semaphores with their own quirks), whereas an exclusive file handle behaves
  identically everywhere and is **released by the OS if the process dies** — a
  crash cannot leave the app permanently unlaunchable.
- **A permissions failure taking the lock lets the app run anyway.** A possible
  second tray icon is better than an app that refuses to start.

### Resource measurement — one target met, one missed

Measured on Windows, Release build, idle:

| Metric | Measured | `PLAN.md` target | Verdict |
|---|---|---|---|
| CPU between polls | 0.05 – 0.2 % | ~0 % | **pass** |
| Working set | ~135 MB | < 60 MB | **fail** |
| Private memory | ~106 MB | — | — |
| Growth over 2 min | **−9.6 MB** | no growth | **pass** |

Two things worth separating:

1. **There is no leak.** Memory *falls* by about 10 MB as the GC settles, which is
   the signal that matters: the tray icon allocates a `RenderTargetBitmap` on
   every poll, and a steady climb here would have meant one was not being
   disposed. It is.
2. **The absolute figure is more than twice the target.** GC tuning
   (`ServerGarbageCollection=false`, `ConcurrentGarbageCollection=false`,
   `RetainVMGarbageCollection=false`) made **no measurable difference** —
   ~137 MB before, ~135 MB after, which is noise. Those settings are kept because
   they are the right shape for a process that idles for days, **not** because
   they were shown to help. The csproj comment says so, to stop a later reader
   assuming they are load-bearing.

The 60 MB figure was written in Phase 0 before anything existed and looks
unrealistic for Avalonia on .NET. The remaining lever is trimmed, self-contained
publishing in Phase 7, which typically helps but is unlikely to halve this.
**This needs a decision rather than a quiet tick: revise the target, or keep
chasing it.** The box is deliberately left unchecked in `PLAN.md`.

### Caveats to carry forward

- All measurements are Windows-only. macOS and Linux figures are unknown.
- The single-instance guard's cross-platform behaviour is tested by unit tests
  that run everywhere, but "kill the process and relaunch" is only covered by the
  QA checklist.

## Logging pipeline (2026-09-04, after Phase 6)

Not on any phase's checklist — it fell between Phase 3, which built the redactor,
and Phase 5, which built the app. `CLAUDE.md` §6 asks for it and
`docs/security.md` threat T1 assumed it was live. It was not: nothing wrote logs
at all, so nothing leaked, but the gap had to close before the first release.

391 tests.

### What landed

- **`RollingFileLoggerProvider`**: appends to `claudestatus.log` in the config
  directory, rolls at 1 MB, keeps three old files.
- **Wired in `AppServices.AddClaudeStatusLogging`** with
  `RedactingLoggerProvider` as the **outermost** provider, so there is no path
  from a log call to the file that skips redaction.
- **Loggers injected** into the config store, snapshot cache, usage provider,
  monitor, credential service and single-instance guard — all of which already
  accepted an optional `ILogger` and were silently getting `NullLogger`.
- The log path is shown in the Info window so someone filing a bug can find it.

### Design decisions worth remembering

- **No Serilog or NLog.** What this needs is "append a line, roll at a megabyte,
  keep a few", which is a few dozen lines. `CLAUDE.md` §8 wants a real
  justification for a package, and a logging framework sitting next to the
  credential path is more surface than this earns.
- **Nothing in the file provider may throw.** A tray app dying because its log
  file is locked or the disk is full would be a far worse bug than a missing
  line. Every failure path gives up silently, and a test covers it.
- **`ClearProviders()` first, and no console or debug sink.** A second sink would
  be one the redactor does not cover in a published build, and there is no
  console anyway.
- **`System.Net.Http.HttpClient` is filtered to Warning.** It logs four lines per
  request at Information, which at one poll a minute would bury everything worth
  reading. It also logs request headers — including `Authorization` — at Trace;
  the redactor catches those regardless, but keeping the category quiet means the
  question never arises in a normal build.
- **Scopes are ignored by both providers.** Never put a secret in a scope.

### Verified against a real run

Ran the Release build with a clean profile. It read the Claude Code login, made
a live request that returned 200, cached the snapshot, and wrote:

```
[INF] JsonConfigStore: No settings file yet; using defaults. This is a first run.
[INF] TrayApplicationController: ClaudeStatus starting. Source: ClaudeCodeLogin. Poll interval: 00:01:00.
```

Grepping the real log and the real cache for `sk-ant-`, `Bearer`,
`anthropic-organization-id` and `anthropic-workspace-id` found nothing. That is
the first end-to-end confirmation that the whole stack works: credential read,
live fetch, parse, cache, render, log.

`docs/security.md` threat T1 moves from "designed" to done, and its checklist

## Memory investigation (2026-09-04)

Prompted by Phase 6's memory target failing. Visual Studio 2022 Professional is
installed, but its memory profiler is GUI-only; the same engine is available
through the `dotnet-counters` / `dotnet-gcdump` CLI, which is what was used.

### The measurements

| Build | Working set | Private | Modules |
|---|---|---|---|
| Bare Avalonia, no windows, no DI, no HTTP | **86.0 MB** | 72.2 MB | 108 |
| ClaudeStatus, framework-dependent | 145.3 MB | 117.4 MB | 174 |
| ClaudeStatus, trimmed self-contained | **102.9 MB** | 78.6 MB | 148 |
| `PLAN.md` target | < 60 MB | — | — |

Managed heap, from a GC dump of the running app: **4.8 MB across 48,673 objects.**
Allocation rate at idle: **32 KB/s**, with **zero GC collections in 20 s**.

### What this means

- **Our code is not the problem.** 4.8 MB of managed objects against a 142 MB
  working set means roughly 97 % of the footprint is the .NET runtime, the JIT,
  and mapped native images. There is nothing to optimise in the app.
- **The 60 MB target is unreachable.** An Avalonia app with *no windows, no DI,
  no HTTP and no logging at all* uses 86 MB. The floor is above the target, so no
  amount of work on this codebase can meet it.
- **The 59 MB we add over that floor is mandatory.** Diffing loaded modules, the
  70 extras are almost entirely the HTTPS/TLS stack — `schannel`, `ncrypt`,
  `ncryptsslp`, `ws2_32`, `mswsock`, `DNSAPI`, `IPHLPAPI`, `System.Net.*`,
  `System.Security.Cryptography` — plus DI, JSON and logging. We have to make an
  HTTPS request; none of this is removable.
- **Trimming is worth ~42 MB** (145 → 103 MB working set, 117 → 79 MB private).
  Real, but not enough to reach 60 MB, and it comes with a serious caveat below.

**Recommendation: revise the target to 120 MB working set framework-dependent,
or 105 MB trimmed.** The 60 MB figure was written in Phase 0 before any code
existed and does not survive contact with Avalonia on .NET.

### Three defects found on the way — none of them about memory

Running the trimmed build turned up real bugs that would have shipped in Phase 7:

1. **Trimming silently breaks JSON persistence.** The trimmed build ran, logged,
   and looked healthy — but never wrote its snapshot cache, leaving a 0-byte
   `last-snapshot.json.tmp` behind. `System.Text.Json`'s reflection-based
   serializer was trimmed away, exactly as the IL2026 warnings said it would be.
   Settings would fail the same way the first time someone pressed Save.
   **Fix before any trimmed release: a source-generated `JsonSerializerContext`
   for `AppSettings` and the cache DTO** (also the right answer for AOT).
2. **A failed save leaves its temp file behind.** `JsonConfigStore` and
   `JsonSnapshotCache` both write to `<file>.tmp` then rename. Nothing deletes the
   temp file if serialization throws.
3. **The failure was swallowed completely.** `SaveAsync`'s catch only handles
   `IOException` and `UnauthorizedAccessException`, so the trim-induced exception
   escaped — and the call site is fire-and-forget (`_ = _snapshotCache.SaveAsync(…)`),
   so it faulted unobserved with nothing logged. The cache silently stopped
   working and the app looked fine.

Number 3 is the one worth remembering: a fire-and-forget task with a narrow catch
is how a feature dies quietly.

### Tooling note

`dotnet-counters` and `dotnet-gcdump` were installed as global tools. Useful
recipe for next time:

```
dotnet-counters collect --process-id <pid> --counters System.Runtime --format csv
dotnet-gcdump collect --process-id <pid> --output heap.gcdump
dotnet-gcdump report heap.gcdump          # text report, no GUI needed
```

### Follow-up: NativeAOT (2026-09-04)

Tested compiling with no .NET runtime dependency at all — `PublishAot=true`.
**It works.** The whole app compiles to a single 22 MB native `.exe` that runs,
logs, and fetches usage with no runtime installed.

| Build | Working set | Private | Modules | On disk |
|---|---|---|---|---|
| Framework-dependent (current) | 145.3 MB | 117.4 MB | 174 | ~1 MB + runtime |
| Trimmed self-contained | 102.9 MB | **78.6 MB** | 148 | 149 MB |
| **NativeAOT** | **95.4 MB** | 101.7 MB | 97 | 22 MB exe (222 MB dir) |
| Bare Avalonia floor | 86.0 MB | 72.2 MB | 108 | — |
| `PLAN.md` target | < 60 MB | — | — | — |

Reading these:

- **NativeAOT wins on working set (95 MB) and enormously on distribution size** —
  a 22 MB single file with no runtime dependency, against 149 MB for trimmed
  self-contained. It also loads 97 modules instead of 174.
- **Trimmed self-contained wins on private memory** (78.6 vs 101.7 MB). AOT shares
  nothing with other .NET processes, so all of its memory is private; the
  framework builds share mapped runtime images. Which number matters depends on
  whether anything else on the machine is running .NET.
- **Neither reaches 60 MB**, and neither can: the bare Avalonia floor is 86 MB.
  AOT lands 9 MB above a completely empty Avalonia app, which is about as close to
  the floor as this app can get.

**The same JSON defect reproduces under AOT** — a 0-byte `last-snapshot.json.tmp`
and no cache written, with IL3050 warnings saying so at build time
(`JsonStringEnumConverter` also needs its generic `JsonStringEnumConverter<TEnum>`
form). This confirms the source-generated `JsonSerializerContext` is a
prerequisite for *either* trimming or AOT, not just a nicety.

Everything else survived AOT intact: DI, the HTTP stack, the tray, the logger,
compiled bindings. Only reflection-based JSON broke.

**Toolchain note.** The AOT link step shells out to `vswhere.exe`, which is not on
`PATH` by default. Without it the build fails at the very last step with a
misleading MSB3073. Add `C:\Program Files (x86)\Microsoft Visual Studio\Installer`
to `PATH`, or build from a Developer Command Prompt. Worth putting in the CI
workflow when Phase 7 gets there.

## JSON source generation — trimming and AOT unblocked (2026-09-04)

Fixes the defect the memory investigation turned up: reflection-based
`System.Text.Json` works in a normal build and is **silently removed** by
trimming and AOT, so a trimmed build ran, logged and looked healthy while quietly
never writing its snapshot cache. Settings would have failed the same way on the
first Save.

398 tests.

### Why source generation rather than a different library

- **Newtonsoft.Json would be worse.** It is entirely reflection-based, has no
  trim or AOT story, and would add a dependency to fix a problem it makes bigger.
- **Only two files were ever affected.** The AOT warnings named `JsonConfigStore`
  and `JsonSnapshotCache` and nothing else. `UsageResponseParser` — the one
  handling the untrusted API response — was already safe, because Phase 2's
  paranoia about the drifting schema led it to `JsonDocument` and
  `Utf8JsonReader` rather than `Deserialize<T>`. Being defensive about the data
  happened to make it AOT-clean.
- **`System.Text.Json`'s own source generator** is the official answer, adds no
  dependency, and is what the IL2026/IL3050 warnings explicitly tell you to do.

### What changed

- **`ClaudeStatusJsonContext`**, a `JsonSerializerContext` listing `AppSettings`
  and the cache DTO. Options live on the attribute because the generator must see
  them at compile time; `UseStringEnumConverter` replaces
  `new JsonStringEnumConverter()`, whose non-generic form needs runtime codegen
  and had its own IL3050 warning.
- **`CachedSnapshot` promoted** from a private nested record to an internal
  top-level type so the generator can reach it.
- Both stores now call the `JsonTypeInfo` overloads. The reflection overloads are
  gone from the codebase.

### The two defects that let this hide

1. **A failed write left its temp file behind.** Both stores write to `<file>.tmp`
   and rename; nothing deleted the temp file when serialization threw. That
   0-byte `last-snapshot.json.tmp` was the only visible symptom of the whole bug.
   Both now clean up, with tests.
2. **The failure was swallowed twice over.** `SaveAsync` caught only `IOException`
   and `UnauthorizedAccessException`, so the trim-induced exception escaped — into
   a bare `_ = _snapshotCache.SaveAsync(…)` at the call site, where it faulted
   unobserved with nothing logged. The catch is now deliberately broad (a missing
   cache must never take the app down) and logs; the call site observes the fault
   and logs it too.

### Result

| | Before | After |
|---|---|---|
| IL warnings, AOT publish | 18 | **0** |
| IL warnings, trimmed publish | 9 | 1 (in the runtime's own COM activator, not ours) |
| AOT: snapshot cache written | no, 0-byte `.tmp` | **yes, complete** |
| AOT working set | 95.4 MB | 96.0 MB |

Verified by running the AOT build against a clean profile: it wrote a full
`last-snapshot.json` with real usage data and left no temp files.

**Trimming and NativeAOT are now viable for Phase 7.** The remaining COM warning
comes from `BuiltInComInteropSupport`, which the Avalonia template sets and
Windows needs.

### Worth remembering

A fire-and-forget task with a narrow catch is how a feature dies quietly. Nothing
crashed, nothing logged, and the only trace was a zero-byte temp file.

## First visual inspection — a real bug (2026-09-04)

Ran the app and looked at it. The Config window opens correctly on first run and
renders properly (live screenshot of the running process). The Details and Info
windows were captured offscreen with headless Skia, and the tray icon was
rendered at real notification-area sizes on both tray colours.
Images in `docs/screenshots/`.

### The bug: the tray icon is nearly invisible on a light taskbar

`TrayIconRenderer.NormalColor` is `#E6E6E6` — near-white. On the Windows 11 dark
taskbar it is crisp at every size. On a **light** taskbar (`#F3F3F3`) the normal
state is a ghost: "7" and "61" are barely-there outlines, and the Ring mode's
arc all but disappears.

What holds up on both: the red alert states (`100`, `88`, `!`) are clearly
visible, and `--` for no-data is marginal but readable.

So the icon is legible exactly when something is wrong, and invisible the rest of
the time — on the light theme, which is the Windows default for a fresh install.

This is a Phase 5 defect. `docs/qa-checklist.md` §3 asks whether *the red* is
visible on both backgrounds; it is. Nobody thought to ask about the normal state,
which is the one that fails.

**Why macOS is unaffected:** the template-icon mechanism recolours the glyph to
suit the menu bar automatically, which is exactly why `IsTemplateIcon` exists.
Windows and Linux have no equivalent — the bitmap is drawn as given.

**Fix options, not yet chosen:**
1. Read the Windows taskbar theme
   (`HKCU\…\Themes\Personalize\SystemUsesLightTheme`) and pick the ink colour to
   match. Correct, but Windows-specific and needs a re-render when the user
   switches theme.
2. Draw a contrasting outline or shadow under the glyph so it reads on any
   background. Platform-independent, slightly busier at 16 px.
3. Pick a mid-tone that survives both. Simplest, and worst-looking on both.

Option 2 is the most robust for Linux, where there is no reliable theme signal
at all. Option 1 gives the cleanest result on Windows. They combine well.

### Also confirmed working

- Numbers are legible down to **16 px** on a dark tray — the 2x supersampling
  does its job.
- The Ring renders correctly at 0 %, 61 % and 100 %, with the sweep starting at
  twelve o'clock.
- The `!` credential-alert glyph is unmistakable at every size on both themes.
- MinVer is stamping the version: the Info window shows
  `0.0.0-alpha.0.10+829cb768…`, from git, never hand-edited.
- The stale banner, the red bars past the threshold and the "resets in 2h 36m"
  countdowns all render as intended.

### Method note

The live taskbar could not be screenshotted: it is set to auto-hide on this
machine, and it only reveals for genuine user input, which a script cannot
convincingly fake. The icon renders are produced by calling the real
`TrayIconRenderer` and compositing onto the actual tray colours — accurate for
judging legibility, but not a substitute for `docs/qa-checklist.md` §2 on a real
desktop.

## Tray icon contrast — two rendering bugs fixed (2026-09-04)

Both found by rendering the icon and looking at it, and both had passed tests
that only asserted a bitmap came back non-null.

### 1. Invisible on a light taskbar

The ink was `#E6E6E6` regardless of the tray colour, so the icon vanished on the
Windows light theme — readable only once it turned red, which meant it was
legible exactly when something was wrong and invisible the rest of the time.

Fixed with `ITrayThemeProvider`:

- **Windows** reads `SystemUsesLightTheme` from the Personalize key. Note that is
  the *system* value, which governs the taskbar; `AppsUseLightTheme` governs app
  windows and is a different setting. A user can perfectly reasonably run light
  apps on a dark taskbar, and reading the wrong key would invert the icon for
  them.
- **macOS** needs nothing — a template icon is recoloured for the menu bar.
- **Linux** has no portable signal, so it reports `Unknown`, and the renderer
  draws the glyph with a contrasting outline that reads on any panel colour.

The theme is read on every render rather than cached, so switching the system
theme takes effect on the next poll with no change-notification plumbing.

The alert red is also split: `#FF5D5F` on dark, the darker `#C4181B` on light,
because the dark-tray red is washed out on a light panel.

### 2. The ring collapsed to a dot at 100 %

`ArcTo` from a point back to itself is degenerate and rendered as a speck — so
the ring disappeared at exactly the moment it mattered most. A full sweep is now
drawn as an ellipse.

This one is worth dwelling on: the existing test was called
*"The\_ring\_renders\_at\_both\_extremes"* and asserted `bitmap.Should().NotBeNull()`.
It passed against a single dot. The bug was visible in the very first icon sheet
and I misread it as correct.

### The halo took two attempts

The first outline stamped the same text at eight offsets. That looked acceptable
magnified and turned into a smeared, doubled mess once downsampled to 16 px. It
now strokes the real glyph geometry from `FormattedText.BuildGeometry`, which
keeps the letterforms intact at every size.

### Tests that can actually catch this

`TrayIconContrastTests` reads the rendered bitmap back with `CopyPixels` and
asserts on real pixels: mean luminance is high on a dark tray and low on a light
one, the unknown-background render paints strictly more pixels than the plain
one, a full ring paints more than a quarter ring, and every state on every
background paints something.

This required switching the headless test fixture from the stub drawing backend
to Skia (`UseHeadlessDrawing = false`). With the stub, nothing is rasterised and
every pixel assertion would have passed vacuously — which is its own trap.

407 tests. Refreshed contact sheet in `docs/screenshots/tray-icons.png`, now
covering four combinations: dark and light with a known background, and both
again with `Unknown` to show what Linux gets.

### Worth remembering

Two bugs, both in code with green tests, both obvious within seconds of looking
at the output. `NotBeNull()` on a bitmap tests that rendering did not throw. It
says nothing about whether anything was drawn, or whether a human could see it.

## 2026-09-05 — The details popup opened off-screen

Reported after a real click: the window appeared with its left edge near the tray
icon and its body hanging off the bottom-right of the screen.

Two units were being mixed. `Screen.WorkingArea` and `Window.Position` are
**physical pixels**; `Window.Width` is **device-independent units**. The old code
anchored the window at `WorkingArea.Right - Width - 12` with `Width` treated as
pixels. On this machine — 3840×2160 at 175 % — the 340-unit window is really
595 px wide, so it started 352 px from the right edge and ran 243 px past it. The
height was worse: a hardcoded guess of 320 against a real 735 px put the bottom
about 400 px below the taskbar.

Three further problems in the same eight lines: the window was positioned once at
construction and never again; it was positioned *before* its first layout pass, so
with `SizeToContent="Height"` its height did not exist yet; and nothing clamped
the result to the screen.

`TrayPopupPlacement` now does the geometry as a pure function — convert through
`Screen.Scaling`, infer which edge the taskbar is on from the inset between
`Bounds` and `WorkingArea`, then clamp into the working area. The clamp is what
actually guarantees the window is visible; the anchor is only a preference. The
controller repositions on every open and on `SizeChanged`.

Inferring the taskbar edge is slightly more than the bug required. It means a top
bar (macOS) gets the popup hanging from the top rather than as far from the status
item as possible. Untested there, like the rest of the macOS path.

15 tests: every scaling from 1.0 to 2.0, taskbar at bottom/top/left, a monitor at
a negative virtual-desktop origin, a popup taller than the screen, and NaN or
absurd scaling values.

An incidental find: `ClaudeStatus.Core.Tests` had been silently reporting "no
tests ran" (`BadImageFormatException` in the xUnit collection runner) because a
locked build had left its output directory half-copied. Deleting `bin`/`obj`
fixed it. Worth knowing that exit code 8 from the test platform means *nothing
ran*, which is not the same as passing.

## 2026-09-05 — Localization: en, es, ca, de, fr

Asked for five languages, and for adding a sixth to be "just translating the
resources". Those two goals pull in different directions — `.resx` gives the best
tooling and compile-time-ish safety but needs a rebuild; loose files need no SDK
but lose every check. The app does both: satellite assemblies for the five
shipped languages, plus a `lang/*.json` folder probed at startup that overrides
them key by key.

### The layering is the part that matters

Three sources per key: `lang/<culture>.json`, then the satellite `.resx`, then
English. Because it resolves per key rather than per file, a three-line JSON file
overrides exactly three strings and everything else keeps working. There is no
state where adding a file blanks the interface.

### Keys, not sentences, below the UI

The bigger change was structural. `CredentialFormat.Describe` returned English;
so did `CredentialTestResult.Message`, `ISecretStore.Description`,
`IAutostart.Description`, `IUsageProvider.Name`. All of them already had an enum
or a stable identity next to the prose, so they became `DescribeKey`,
`MessageKey`, `DescriptionKey`, `NameKey`. Core and the platform projects now
contain no user-facing English at all, which is the only way the same explanation
can appear in five languages.

`CredentialTestResult` needed one extra field — `SessionPercent` — because "works,
and you are at 61 %" cannot be expressed as a bare key without Core composing a
sentence.

### InvariantGlobalization was silently fatal

Every localization test failed at once with `CultureNotFoundException: Only the
invariant culture is supported`. `Directory.Build.props` had
`InvariantGlobalization=true`, presumably for publish size. Under it the runtime
refuses `CultureInfo.GetCultureInfo("es")`, so no satellite set can ever be
selected — the app is English-only by construction, whatever the .resx files say.

Turning it off costs almost nothing on Windows and macOS, where ICU comes from
the OS. On Linux it means libicu must be present, which desktop distributions
have. It also woke four CA2101 P/Invoke marshalling errors in the libsecret
bindings, now fixed with `BestFitMapping = false, ThrowOnUnmappableChar = true`.

### The one string in settings.json

`AppSettings` deliberately had no `string` properties, guarded by a reflection
test whose comment said adding one should "force a conscious decision". This is
that decision, documented in `docs/security.md` §4.1: `LanguageTag` is capped at
12 characters and must match `^[a-z]{2,3}(-[A-Za-z0-9]{2,4})?$`, which no token
can satisfy. The test now carries an explicit allowlist plus cases proving that
token-shaped and traversal-shaped values are discarded, including through a real
save.

An enum of the five languages would have been airtight, but it would make a
language added by JSON file unselectable — which is the whole point of that
mechanism.

### A crash the tests could not have found

Switching language rebuilds the tray menu, because backends disagree about
whether a `NativeMenuItem` header can change after the menu is handed to the OS.
The first version reused the four mode items in the new menu, and Avalonia threw
`InvalidOperationException: already has a parent` — on startup, every time, since
applying the saved language fires the change notification. The app logged
"starting" and died. Found only by running the executable and reading stderr; the
headless tests never construct a real `TrayIcon`.

### Tests that keep the five files honest

A string-keyed resource system trades compile-time errors for runtime blanks, so
the checks were put back deliberately: identical key sets across languages,
identical `{0}` placeholders, no blank values, no credential-shaped values, every
`L[Key]` in AXAML resolves, and every declared key is used somewhere. That last
pair scans the source text, since AXAML keys exist only inside binding strings.

Writing them found a real defect immediately — the AXAML scanner matched `L[Key]`
inside an explanatory XML comment. It also revealed that 17 tests had been
silently skipping, because the repository-root walk looked for `ClaudeStatus.sln`
and this repository uses `ClaudeStatus.slnx`. A test that skips is not a test that
passes, and nothing about the summary line said so.

491 tests. All five languages rendered headlessly and inspected:
`docs/screenshots/languages/`. Spanish shows `43,5 %` with a comma, which is the
sort of thing that makes a translation feel finished rather than applied.

## 2026-09-05 — A second window: the full report

The details popup is an OSD — glance, read three numbers, dismiss. Asked for a
second window for the extended information, reachable from a button in the popup
and from the tray menu. Two windows, deliberately different in kind:

| | Details popup | Report window |
|---|---|---|
| Opens | Left click on the tray icon | Tray menu, or "More…" in the popup |
| Position | Anchored to the tray corner | Centred, OS default |
| On focus loss | Hides | Stays open |
| Resizable | No | Yes |
| Taskbar entry | No | Yes |

The report has to survive being clicked away from: its whole purpose is comparing
numbers against claude.ai in a browser, and hiding on deactivate would make that
impossible. That single difference drives most of the others.

### Most of the work was in the parser, not the window

`GET /api/oauth/usage` returns far more than the three percentages we were using.
The parser read `percent` and `resets_at` and dropped the rest on the floor.
Now also read: `severity`, `kind`, `is_active`, `scope.model.display_name`, the
three `*_dollars` figures, `locked_reason`, and the whole `spend` and
`extra_usage` blocks.

`UsageWindow` grew these as `init` properties rather than positional parameters,
so `UsageWindow.Create(percent, resetsAt)` and every existing call site still
compile while record equality still covers the new fields. `UsageSnapshot` has a
hand-written `Equals`, so `Spend` and `ExtraUsage` had to be added there by hand —
easy to forget, and the consequence would be the report going stale while
claiming to be live, since the app skips re-rendering on an unchanged reading.

`MoneyAmount` keeps minor units and an exponent rather than converting on parse,
because the exponent is what says where the decimal point goes and currencies
disagree. It formats the number with the viewer's culture but prints the currency
code verbatim: formatting as `"C"` would render a USD amount with the viewer's own
symbol, so $12.34 read in Spain would claim to be €12,34.

### Severity is shown, not acted on

`severity` is the source's own opinion — the capture has the Fable window at 88 %
labelled `warning` while the other two are `normal`. It is displayed verbatim and
colours the row, but it does **not** override the user's threshold. Two reasons:
the set is open and undocumented, and the threshold is a setting the user chose.
`IsWarning` is defined as "not normal" rather than "is warning", so a severity we
have never seen is treated as worth noticing rather than silently ignored.

`is_active` is displayed for the same reason and decides nothing: in the capture
the active window was not the one with the highest percentage, so whatever it
means, it is not "the one that matters".

### Saying "off" out loud

The spend and credit sections state plainly that they are switched off rather
than rendering an empty panel. A user opening this window wants to know whether
they are being charged past their plan, and a blank section does not answer that.
"Never set up" and "set up but switched off" get different sentences because they
lead to different next actions.

### What the cache does not carry

`CachedSnapshot` is deliberately flat and decoupled from the domain type, and it
was left that way — it still stores only the three percentages and reset times.
So a report opened before the first successful poll of a session shows the cached
numbers with unknown severity and no spend block. That is honest: those fields
genuinely were not persisted. Widening the cache would mean versioning it against
a schema that has already been observed to drift.

### Verification

25 new resource keys across five languages, 41 new tests (532 total). Rendered
the report and the popup in English and Spanish: `docs/screenshots/report/`.
Rendering caught two things the tests could not — a bare "Fable" line with no
label, and "Obtenido a las sábado, 5 de septiembre…", which is not Spanish. The
timestamp templates are now a neutral "Retrieved: {0}" in every language.

## 2026-09-05 — Theming

Eleven themes, a Theme tab, and theme files that need no rebuild. Four questions
were worth asking first, and all four answers shaped the result.

### A theme declares four colours; everything else is derived

`primary`, `background`, `text`, `alert`. The muted grey, the card and border
colours, the warning panel and light-versus-dark are all computed from those.

That is the whole design. Asking a theme author for a grey invites them to pick
one against the wrong background and ship something unreadable; deriving it as
the text colour pulled 45 % toward the background makes it correct by
construction and tints it, so a warm theme gets a warm grey rather than a neutral
one dropped on top. `IsDark` is read from the background's luminance rather than
declared, so it cannot disagree with the colours it describes.

### Fluent does most of the work

Restyling every built-in control by hand would be an enormous amount of AXAML.
Instead `ThemeApplier` sets `RequestedThemeVariant` so Fluent renders its own
controls light or dark, and fills `SystemAccentColor` plus its six Light1-3 and
Dark1-3 steps by blending the primary toward white and black. Buttons, sliders,
checkboxes and the combo box then match a hand-picked primary through every
hover and pressed state, from one declared colour.

Our own surfaces use `Theme.*` brushes bound with `DynamicResource`. A
`StaticResource` would resolve once and the picker would appear to do nothing
until the window was reopened.

### The tests found a real problem, then a fake one

Every built-in theme is asserted to clear WCAG 4.5:1 on body text and 3:1 on the
derived grey. All eleven passed first time, which is what the palette design was
for.

The alert-versus-primary check was harder to write than it looks. The first
version used contrast ratio and failed Dark, Ocean and Nebula — all of which are
fine. Contrast is a **brightness** comparison, and a blue primary beside a red
alert of similar lightness scores about 1.06 while being impossible to confuse.
Rewritten as straight-line distance in RGB, it passed those three and correctly
failed **Sakura**, whose alert really was a crimson a few degrees from its pink
primary. That one was a theme bug and the theme was changed, not the test.

### The security guard fired again, as intended

`AppSettings` gained two more strings — `ThemeId` and `FontFamily` — and the
reflection test failed the build until each was allowlisted with a normalizer and
a pair of tests. `docs/security.md` §4.1 is now a table of three fields rather
than a paragraph about one.

`FontFamily` is the loosest field the settings file has ever had, so it carries
the most: a 64-character cap, a charset restricted to what real font stacks
contain, and a `Redactor.LooksRedacted` check on top. The cap alone already stops
a whole token fitting; the check is belt and braces on the one field where free
text is genuinely expected. `ThemeId` doubles as a path segment under `themes/`,
so its validation is also the path-traversal defence.

### Opacity is background-only

`Window.Opacity` would fade the numbers too, and a number you have to squint at
is the one thing the popup must not produce. The window is transparent and a
`Border` inside it carries an alpha background, so the text stays fully opaque at
every setting. Where a compositor refuses transparency — some Linux desktops —
the border simply paints opaque and nothing else changes.

### Not themed

The tray icon. It sits on a taskbar this app does not control and keeps its own
contrast logic. A themed 16 px glyph would be invisible on half of all systems,
which is a bug this project has already shipped once (`92acf84`).

## 2026-09-05 — Popup opacity starts at zero

The slider had a 0.3 floor, put there on the assumption that a fully transparent

Two changes beyond moving the minimum:

- The **border fades with the panel**. An opaque outline at zero opacity would

- The tick frequency went from 5 to 10, because the slider now spans 0-100 rather

leak into the report or config windows.

## 2026-09-05 — Opacity became transparency

## 2026-09-05 — Bigger, cleaner tray digits

Two requests: make the number bigger by two pixels, and antialias it.

### The antialiasing was a real bug, not a polish item

`TextRenderingMode` was left `Unspecified`, which on Windows means **subpixel**
antialiasing. Subpixel AA works by tinting the edge pixels red and blue on the
assumption they sit on a known opaque background — and this icon has an alpha
channel and sits on a taskbar whose colour we do not control. The fringes were
wrong on every system, and worse the more the tray downscaled the bitmap.

It is now explicitly `TextRenderingMode.Antialias` (grey), which is what a
transparent icon needs, plus `EdgeMode.Antialias` for the ring and halo.

Hinting is set to `None` for a related reason: grid-fitting stems helps text at
its final size, but this glyph is drawn at 64 px and downsampled by the tray to
16, 24 or 28. Snapping to a grid the glyph will never be displayed on distorts
the shapes on the way out.

`RenderOptions.TextRenderingMode` is obsolete in Avalonia 12 — it moved to
`TextOptions`, pushed with `PushTextOptions`.

### Bigger, and safely so

`GlyphBoost` adds 2 nominal pixels (4 in the supersampled bitmap) to the glyph.
On its own that would risk clipping "100", so `FitWidth` measures the text and
shrinks the size in 4 % steps until it fits. That inverts the relationship: the
constants can now be raised freely and the fitter guarantees the result, rather
than the constants having to be conservative enough never to overflow.

Which in turn made a second constant redundant. There used to be a separate,
smaller fraction for three-digit readings — a hand-tuned guess at the width three
digits need. `FitWidth` measures that exactly, so both cases now request the same
size and "100" shrinks by precisely as much as it must. It came out visibly
larger than the old guess.

### Tests

`InkBounds` reads the rendered bitmap back and returns the bounding box of the
painted pixels. Two new assertions: no ink touches the outer row or column at 7,
61 or 100 % (nothing is clipped), and "100" still spans more than 75 % of the
width (the fit shrinks, it does not collapse). Both are the kind of failure that
`NotBeNull()` on a bitmap would have sailed past — the same lesson as `92acf84`.

## 2026-09-05 — Left click toggles the popup

Asked for: first click shows the OSD, a second click hides it. The obvious
implementation is wrong, and wrong in a way that looks like the icon is broken.

The popup hides itself when it loses focus — that is how a tray popup is meant
to behave, and it has been in `DetailsWindow` since Phase 5. Clicking the tray
icon takes focus away from the popup, so by the time the click handler runs the
window has **already** hidden and `IsVisible` is `false`. A straightforward
`IsVisible ? Hide() : Show()` therefore reopens the window the user just asked to
close, and the icon appears to ignore the click entirely.

`TrayPopupToggle` resolves the two into one gesture: a click arriving within
250 ms of the popup dismissing itself is the closing half of that gesture, not a
request to reopen. The deactivation and the click are two halves of one mouse
press and land milliseconds apart, so the window is generous; it is still far
shorter than any deliberate second click.

Three outcomes rather than a boolean — `Show`, `Hide`, `Ignore` — because the
`Hide` branch is genuinely reachable: a backend that delivers the click without
deactivating the window first would land there, and dropping it would make this
work on Windows and silently fail elsewhere.

A negative elapsed time means the clock moved backwards (resume from sleep, an
NTP correction) and is treated as "long ago". Refusing to open the window is a
worse failure than opening one the user meant to close.

Pure and separated from the controller, so the timing rule is tested without a
window, a tray or a real clock — which matters, because getting it wrong is
invisible to code review and indistinguishable from an unresponsive icon when
clicking around by hand.

Reported from the running app: the Fable bar said **"reset time unknown"**. The

— the endpoint returns `resets_at: null` for a scoped window it has nothing to

weekly_all     …T22:59:59.968265+00:00

## 2026-09-05 — A stale reading is drawn faded

Asked what the icon shows with no API connection. The answer exposed a gap:
**nothing changed on it at all.**

`IndicatorAlert.Unreachable` is deliberately not drawn — a network failure
resolves itself and must not nag, which is why only a missing credential gets the
red `!`. But that left the icon showing the last known percentage in full-strength
ink, visually identical to a live reading. The staleness was honest everywhere
except the one surface people actually look at: the tooltip said "(stale)", the
popup showed a banner with the age, the report said so too, and the icon quietly
presented a three-hour-old 61 % as current.

The icon now fades to 55 % opacity when `snapshot.IsStale`.

### Alpha, not colour

Recolouring a stale reading to grey would have been easier and worse. A stale
95 % is still the best evidence available that the user is near their limit, and
it should still be red. Fading says "this is old"; recolouring would also say
"and I have forgotten what it was".

Scaling alpha rather than blending toward a background colour is also what a
transparent icon actually wants: the taskbar shows through by exactly the amount
taken away, whatever colour that taskbar happens to be. It works with the macOS
template-icon mask for the same reason — that mask is read from alpha.

`Palette.Fade` scales the existing alpha rather than assigning one, which matters
for the ring's track: it is already semi-transparent, and assigning would make a
faded track *more* solid than a fresh one.

### Measuring a fade

The existing pixel helper computes mean luminance, and that is the wrong
instrument here — fading changes alpha and leaves the hue alone, so a dimmed red
glyph contains exactly the same red, just less of it. `InkMass` sums the alpha
channel across the bitmap instead.

Six new tests: the fade happens on all three backgrounds and in ring mode, it
stops well short of illegible, the alert ink survives it, and the `!` for a
missing credential is never faded — that one is actionable and must not be
softened.

## 2026-09-05 — Three bars and a percent sign in the icon

The icon now carries all three metrics: the chosen one as a number with a smaller
`%`, and session / week / Fable as three 2 px bars along the bottom, 2 px clear
of every edge.

### The one themed pixel

The bars' **fill** uses the theme's primary, or its alert colour past the
threshold, so they match the popup exactly as asked. That is a deliberate
exception to the rule that the icon is never themed — a rule that exists because
the taskbar's colour is not ours to choose, and a themed glyph can vanish on it.

What keeps the exception safe is that the **track** is drawn in the icon's own
contrast-aware ink. A theme whose primary sits close to the taskbar colour still
produces a bar with a visible footprint; only the fill inside it goes quiet.
Without the track, "match the popup" would have meant "sometimes invisible".

`IStatusIndicator.SetBarStyle` is a default-implemented no-op, so an indicator
that draws no bars — the macOS `NSStatusItem` with inline text sketched in
Phase 8 — is not obliged to care.

### Layout, and what it costs

The bars take a 10 px strip off a 32 px canvas, and the `%` takes horizontal
room, so **the number is smaller than it was**. That is unavoidable: the icon is
the same size and now shows four things instead of one. `Fit` already measured
the glyph against a box, so it only needed to be told the box is shorter — no
font size was recomputed by hand.

At 24 px and above the three bars resolve cleanly. **At 16 px they do not** —
three 1 px bars with sub-pixel gaps blur into a single band. The colour still
reads, so it degrades to "there is a bar area" rather than to nonsense, but
anyone on a 100 % display gets much less from them than the 175 % display this
was designed against. `BarHeight`, `BarGap` and `BarMargin` are the knobs.

### The test I got wrong first

`The_bars_are_only_drawn_when_the_caller_supplies_colours` originally asserted
that nothing was painted on the bar row without a style. It failed: with no bars
the glyph keeps the whole box and paints there quite happily. What actually
distinguishes a bar is that it spans the full track width, margin to margin,
which no row of a centred glyph ever does. Rewritten around `Span`, it passes and
now tests the right property.

## 2026-09-05 — The number was being fitted to the wrong box

Reported: the digits look small, the Windows tray icon is 24×24, and hovering
shows a rounded rectangle with a lot of unused space next to the network icon.

Part of that space is Windows' own: the tray *button* is larger than the icon it
holds, and that padding is not ours to fill. But the icon itself really was
wasting about a third of its height, and the cause is worth writing down.

### FormattedText.Height is not the height of the text

It is the height of the **typographic line** — ascender, descender and leading.
Digits occupy only the cap height in the middle of that, with empty space above
for accents that never appear and below for descenders that digits do not have.
Fitting to it therefore guaranteed a large invisible margin, and the fit then
shrank the glyph further to make that margin fit.

`FitToInk` measures `BuildGeometry(...).Bounds` — the marks the glyph actually
makes — and scales so *those* fill the box. Positioning subtracts the ink's own
offset, which turns "draw the line box here" into "put the digits exactly here".
The number came out about 40 % taller with no change to the icon's size.

The iteration also changed direction. The old fit could only step *down* 4 % at a
time from a guessed starting size, so it could never reclaim space the
measurement was wasting. Glyph outlines scale linearly with font size, so one
proportional step lands almost exactly on the answer; three passes is ample.

`GlyphBoost` and `GlyphFraction` are now just a starting guess for that fit
rather than the thing that decides the size.

### Also

- **Bar gap removed**, as asked. At 16-24 px a 1 px gap is sub-pixel anyway, so
  it bought nothing and cost height the number wanted. The three now read as one
  stacked block.
- **`GlyphMargin` is 1 px**, deliberately smaller than the bars' 2 px. A tray
  icon that leaves a visible frame of empty space looks undersized beside the
  system's own, which fill their box.
- `BarBounds` / `BarCentreY` / `GlyphBoxHeight` are exposed to the tests, which
  had hard-coded the row arithmetic and went looking in the wrong place the
  moment the gap changed.

### Two tests wrong for the same reason

Both assumed things about the glyph that stopped being true once it filled its
box. One asserted no ink on the bar row without bars — but the glyph now uses
the full height and paints there. The other distinguished bars from glyph rows
by *extent*, and a row through the digits now reaches both margins too. The real
discriminator is continuity: only a bar paints every pixel between the margins.
`IsSolidTrack` tests that instead.

A third, asserting the ink starts within 6 px of the top, was deleted rather than
loosened: it was a proxy for "the glyph is big", and the test that measures ink
height against the box says that directly.

## 2026-09-05 — Margins to zero, and what actually limits the number

Asked to remove the margins because the number still looked small. Done —
`GlyphMargin` and `PercentGap` are both 0 — but the margins were not the
constraint, and measuring said so plainly.

Instrumented the renderer and read back the ink bounds on the 64 px bitmap:

| reading | ink | width used | height used |
|---|---|---|---|
| `7 %` | 64 × 48 | **100 %** | 100 % |
| `61 %` | 64 × 31 | **100 %** | 64 % |
| `100 %` | 64 × 24 | **100 %** | 50 % |

**The digits are width-bound in every case.** There was no spare width for a
margin to give back; removing it bought a few percent. The height going unused is
a symptom, not a cause — the glyph cannot grow taller without growing wider.

So the thing taking the width is the `%`. Same measurement across sizes:

| `%` size | cap height of `61 %` |
|---|---|
| 0.5 | 31 px |
| 0.4 | 34 px |
| 0.3 | 35 px |
| no sign at all | **43 px** |

Shrinking the sign has sharply diminishing returns; only removing it buys real
room — about **40 % more number**. Settled on 0.4 as the knee: noticeably bigger
digits, and a sign that still reads as a unit rather than a speck at 24 px. The
table is in the constant's own doc comment, so the next person to wonder does not
have to measure it again.

### Three tests were asserting the margin

All three predate the change and encoded "there is a margin" as if it were an
invariant. `The_glyph_never_reaches_the_edge_of_the_icon` was the clearest case:
its name says exactly the thing that is now wrong. The horizontal overrun it
guarded cannot happen any more anyway, since the fit measures the ink and scales
to the box instead of stepping down from a guess.

Rewritten as `The_glyph_never_runs_into_the_bars`, and pinned as *where the strip
begins* rather than as a gap above it — because a glyph filling its box right up
to the boundary is correct, and `7 %` does exactly that. Demanding clear rows
above the bars would have forbidden the very thing this was for.

## 2026-09-05 — A design pass over the windows

The four windows were correct and plain. This pass gives them a shared visual
language so they read as one application rather than four dialogs that happen to
share a palette.

### A type scale instead of local guesses

`Styles/Shared.axaml` now opens with a scale — 11 / 12 / 13 / 15 / 26 — and two
corner radii, and every view takes its sizes from there. The gap between 15 and
26 is the point: a usage percentage is the only thing this app exists to show, so
it gets a size nothing else may use.

Two new classes carry most of the change. `.label` is the small letterspaced grey
above a field or a metric; the letterspacing is what stops 11px text reading as a
cramped block, and it is most of why the popup now looks considered rather than
merely small. `.display` is the headline percentage, with `FontFeatures="+tnum"`
for tabular figures — without it a number ticking from 68 % to 71 % visibly
shifts, because a `1` is narrower than an `8` in most proportional faces, and a
number that twitches every minute looks broken however correct it is.

### The bar is now a drawn control

`Controls/UsageBar` replaces `ProgressBar` in both windows. Avalonia's
`ProgressBar` computes its indicator width in code against named template parts,
so restyling it this far means reproducing a contract that is not public API —
and getting that subtly wrong produces a bar that never moves. Forty lines of
`Render` owe nothing to it, and buy two things the template could not: caps that
stay semicircular at any height, and a floor on the fill width so 1 % is a
visible dot rather than a hairline thinner than its own track. `UsageBarTests`
renders it for real and counts filled columns, including the clamp at both ends.

### Two derived colours, and one that was measured wrong

`Theme` gains `Track` — the groove, deliberately a shade stronger than `Border`,
because a hairline is meant to be noticed only when looked for while a track has
to read as the bar's full extent at a glance — and `OnPrimary`, the label on a
filled accent button.

`OnPrimary` was first written as `Primary.IsDark ? white : black`, which looks
equivalent to picking by contrast and is not. Every primary here has to clear 3:1
against both a light and a dark background, which forces them all into the middle
of the range, and in that middle the two rules disagree for **eight of the
eleven** built-ins. `A_filled_accent_button_is_legible_in_every_theme` failed all
eight immediately; the fix is to measure both candidates and take the better one.

### Fluent's brushes, not our setters

A `Style Selector="Button"` setting `Background` does nothing visible: Fluent's
template paints its `ContentPresenter` from named brushes, and the presenter's
local value wins. `ThemeApplier` now overrides the `Button*`, `TextControl*` and
`ComboBox*` families instead, which reaches every control in the app rather than
the ones a stylesheet remembered to name. Buttons rest on the card surface and
step toward the text colour on hover, so the accent keeps meaning "primary
action" rather than "this is a button"; `.accent` and `.ghost` classes mark the
two exceptions.

Fluent also sizes tab headers at 24px, taller than the window title. In a 480px
settings dialog that made the tab strip the loudest thing on screen; it is now
13px semibold.

### One real bug, found by looking

The stale banner was bound to `IsStale`, which is true before the first poll
returns — when `StaleText` is empty. Every cold start drew an empty pink box.

The first fix keyed the banner off the text being non-empty, which works and
hides the reasoning in a converter in the AXAML. Both view models now expose
`HasStaleReading` instead: **there is a reading and it is old**. The two
questions were being answered by one flag, and `UsageSnapshot.IsStale` answers
the wrong one — it is true when there is nothing to be stale.

The report had the same conflation and a worse symptom: with no reading it set
`IsStale = true` and displayed *"These are the last known values. A refresh has
not succeeded since."* above an empty list, asserting values that did not exist.
`No_reading_is_not_a_stale_one` and
`Having_no_reading_yet_does_not_raise_the_stale_banner` pin both.

Screenshots under `docs/screenshots/` are regenerated: the eleven-theme gallery,
the five languages, both report windows and the config tabs.

## 2026-09-05 — The cold start explains itself

Opening the popup before the first reading arrived showed three empty bars, three
dashes and a one-line status in the footer. That is the state a brand-new install
sits in — possibly forever, if there is no Claude Code login to read — and a row
of dashes reads as *broken*, not as *not set up yet*, to precisely the person who
most needs telling what to do.

The bars now give way entirely and the popup explains itself instead.

### Five states, not one apology

`ApplyEmptyState` maps the monitor's `Failure` to a title and a body:

| reason | title | action |
| --- | --- | --- |
| *(none — first poll)* | Reading your usage… | — |
| `NoCredential` | Not connected yet | Open Config |
| `Unauthorized` | Credential rejected | Open Config |
| `RateLimited` | Asked to slow down | — |
| everything else | Cannot reach Anthropic | — |

The split that matters is the last column. Two of these are things a user can go
and fix; three resolve themselves, and offering a button that opens a window with
nothing relevant in it is worse than offering none. `Refresh` also drops to the
ghost style whenever `Open Config` is showing — two filled accent buttons in one
340px popup is two primary actions, and in that state refreshing is not the one
to take.

Both keys are written out in full in the switch rather than composed from the
state name. `ResourceKeyUsageTests` scans the source for key-shaped literals to
prove nothing in the `.resx` has been orphaned, and it cannot follow a
concatenation — the allowlist exists for that case, and not needing it is better
than using it.

The footer's status line hides while the panel is up. It carries the same
sentence the panel is already showing at full size.

### Wiring

`ConfigRequested` joins `ReportRequested` as an event rather than a direct call:
the controller owns every window's lifetime and is the only thing that can reuse
an already-open Config instead of opening a second one.

Eleven new keys in all five languages. `Every_reason_for_having_no_reading_says_something`
covers all seven `UsageFetchFailure` values including the three with no case of
their own, because a state that falls through to the default must still say

distinct, or the state machine exists without the user being able to see it.

## 2026-09-05 — Phase 7: it can be installed

ClaudeStatus now builds an installer that updates itself. Windows only, by
decision: macOS and Linux packaging is deferred until somebody has actually run
the app on one, because a package nobody can verify is not a deliverable.

### The publish shape, and one deviation

`PLAN.md` asked for self-contained, single-file, trimmed. It ships self-contained
and trimmed, and deliberately **not** single-file. Velopack already delivers one
`Setup.exe`, so single-file buys nothing at the point of delivery — and it costs
the thing that matters afterwards: delta updates diff the published folder file by
file, and a single packed blob changes wholesale every release, turning a 2 MB
delta into a 90 MB download.

The first publish came out at **150 MB**, of which **101 MB was
`libSkiaSharp.pdb` and `libHarfBuzzSharp.pdb`** — native debug symbols that
SkiaSharp and HarfBuzz ship in their packages. They arrive as native runtime
assets, so `AllowedReferenceRelatedFileExtensions` does not reach them; a target
drops every `.pdb` from `ResolvedFileToPublish`, which is safe only because
`DebugType` is `embedded`. 150 MB → **50 MB published, 28 MB installed**.

`SelfContained` had to be conditioned on `RuntimeIdentifier`. It is infectious:
set unconditionally it makes both test projects fail with `NETSDK1151`, because a
self-contained executable cannot be referenced by a project that is not one.

### Trimming, and what was actually checked

Every trim warning is in `Avalonia.DesignerSupport` (the IDE previewer host) or
the COM activator. **ClaudeStatus's own assemblies produce none** — the JSON
source generation from `829cb76` paid off exactly as intended.
`ILLinkTreatWarningsAsErrors` is off for that reason, but `EnableTrimAnalyzer`
still runs at build time under `TreatWarningsAsErrors`, so our own code breaking
trim-safety still breaks the build.

Then the part that mattered: **the trimmed build was launched.** It started, read
the Claude Code login, hit the endpoint and wrote a fresh snapshot two minutes
later, at ~101 MB working set — consistent with the trimmed figure predicted in
the Phase 6 memory investigation, and 34 MB below the untrimmed debug build. The
Spanish satellite assembly is present in the output at 20 KB, so the translations
survived.

### Updates: check now, apply on quit

The user picked the middle option, and it is the one that needs the least code
because it is Velopack's own model. `DownloadUpdatesAsync` stages the new version;
`VelopackApp.Build().Run()` in `Main` installs it at the next start. The app is
never restarted underneath anyone — the popup offers a *Restart now* shortcut and
taking it is optional, which is why the notice is a `.notice` and not a
`.warning`, and why its button is ghost-styled.

Only `ReadyToApply` shows anything. Checking and downloading are the app's
business; a **failed** check especially so — reporting it would put a warning
about our own release infrastructure in front of somebody who opened the window
to look at a percentage, and the next check just retries.

The feed is read anonymously. A token would raise GitHub's limit from 60 requests
an hour to 5000 and would also mean shipping a credential inside the application,
which is the one thing this project does not do (`CLAUDE.md` §1). One check every
six hours is nowhere near sixty.

`AutomaticUpdates` defaults on, and off means the request is not made at all
rather than the notice being hidden — this is the only host the app contacts other
than Anthropic.

### The two strings that had to agree

The release pipeline and the updater are wired together by nothing but a
repository URL in `.releaserc.json` and another in `InfoViewModel.ProjectUrl`,
in different files and different languages. If they disagree, releases go to one
repository while every installed copy checks another, and the only symptom is that
updates silently never arrive. `ReleaseConfigTests` asserts they are equal, that
the update feed files are attached to the release, and that `tagFormat` matches
`MinVerTagPrefix` — a mismatch there would leave every build reporting
`0.0.0-alpha.0` forever.

### What is verified and what is not

Verified locally: the publish, the pack, the installer, the trimmed app running
for real, and `semantic-release --dry-run` loading every plugin — including
`@semantic-release/exec`, whose absence would mean the release tags a version and
attaches nothing.

Not verified: **no workflow has ever run**, because the repository still has no
remote. The dry run stops at `repositoryUrl`, which is precisely the piece a
remote supplies.

`build/pack.ps1` exists so that CI runs the identical command a developer does —
a packaging problem should be reproducible on a laptop, not only visible in a
failed workflow.

## 2026-09-05 — The update path, actually run — and two bugs it found

Phase 7 shipped an updater that had never updated anything. Running it properly
meant installing a real build, publishing a newer one, and watching. It worked,
eventually, and the road there was the valuable part.

The substitution: the feed was a local folder rather than GitHub, via a temporary
edit to `InfoViewModel.ProjectUrl` that was reverted afterwards. Everything else —
the installer, the service, the state machine, the staging, the apply-on-restart
hook — is the shipping code. **The GitHub transport itself remains untested.**

The result, from the app's own log:

```
Update checks: Idle. Installed version: 0.1.4.
Update available: 0.1.5. Downloading.
Update 0.1.5 staged; it will apply on next start.
```

and after a restart, `current/sq.version` read `0.1.5`. `vpk` also produced a
**0.1 MB delta** package beside the 23.6 MB full one, which is the concrete
justification for not publishing single-file.

### Bug 1: every startup failure was silent

The first run produced no update log lines at all — not success, not failure.
The cause was in `App.axaml.cs`:

```csharp
_ = _controller.StartAsync();
```

A bare discard on an async call. Anything thrown after the first log line went
into an unobserved `Task`: the tray icon appears, part of the app never starts,
and the log simply stops mid-sentence. It is now awaited inside a helper that
logs the failure and lets the app continue degraded — an icon reporting "no data"
serves a user better than one that vanishes, but the failure must be recorded.

This was not an update bug. It would have hidden **any** startup failure, for as
long as the app existed.

### Bug 2: property initializers do not survive the JSON round trip

With errors visible, the updater still never started — and now demonstrably
without throwing. It was returning early: `AutomaticUpdates` was **false**, from
a `settings.json` that does not mention it.

`AppSettings.AutomaticUpdates` is declared `= true`. The measurement:

| deserializer | `SchemaVersion` from `{}` |
| --- | --- |
| reflection, default options | 1 |
| reflection, the context's options | 1 |
| **the source-generated context** | **0** |

The generated deserializer constructs the object without running property
initializers, so every absent key comes back as `default`. Not an options
difference — the middle row rules that out. Neither
`GenerationMode = Metadata` nor an explicit `[JsonConstructor]` changed it.

**Why it had never been noticed:** `Normalized()` repairs most of them. An empty
`ThemeId` or a null `Polling` is restored a step later, so those defaults appear
to work while actually being reconstructed. The `Polling ?? new PollingOptions()`
already sitting in `Normalized()` is a fossil of someone hitting this and patching
around it. It surfaced now because `AutomaticUpdates` is the first `bool` whose
intended default is `true`, where `false` is legitimate and nothing downstream can
tell the two apart.

**Severity if shipped:** every existing install would have had updates silently
disabled forever, with no symptom — no error, no notice, just a version that never
moves. The one bug class this app can least afford, since the updater is how any
other fix would reach anyone.

**The fix** applies the principle this codebase already chose for
`OsdTransparency` — *make the do-nothing default zero*. The setting is persisted
inverted as `DisableAutomaticUpdates`, so an absent key means updates are on,
with a `[JsonIgnore] AutomaticUpdates => !DisableAutomaticUpdates` for callers.
`SchemaVersion` is repaired in `Normalized()` (0 is not a version this app ever
wrote). The type now carries a prominent warning that a property initializer is
not a persisted default.

`ConfigStoreTests` gained two tests: one for a settings file predating the
feature, one for the general case. Both failed before the fix.

### Also

- `StartUpdates` now logs the resolved state and installed version at startup.
  "Why did it never update?" was otherwise unanswerable from a bug report: an
  unsupported build and a healthy one that found nothing looked identical.
- `VelopackUpdateService` chooses `GithubSource` or `UpdateManager`'s plain
  path/URL overload by inspecting the feed. That is what made a local-folder test
  possible at all, and it opens nothing up — the value is a compile-time constant
  in a shipped build.
- Measured on the real installed build: **104 MB working set, 72 MB private**,
  against 135/106 untrimmed. `PLAN.md`'s 60 MB target is revised to ~105 MB and
  ticked; 60 MB was unreachable by construction.

The test install was uninstalled and the local feed deleted.

## 2026-09-06 — The number fills the icon's height

Two-digit readings were using 32 of the 48 px above the bars, with an empty band
above and below. They now use 46.

### Why the space was there

`FitToInk` takes `Math.Min(maxWidth / ink.Width, maxHeight / ink.Height)` — one
uniform scale, so the tighter axis decides the size and the other keeps its slack.
For a percentage the tighter axis is always width; that was measured when the `%`
sign was added and is what the `PercentScale` table records. The consequence went
unnoticed: every icon the app has ever drawn had a band of unused pixels.

Scaling y separately spends it, via a `PushTransform` about the top of the glyph
box. Measured on the 64 px bitmap, light panel:

| reading | before | after |
| --- | --- | --- |
| `7` | 48/48 | 47/48 |
| `29` | 32/48 | **46/48** (+44 %) |
| `61` | 33/48 | **46/48** (+39 %) |

A single digit is already height-bound, so it does not move — correctly. The
digits are no longer proportional, which is the trade: at 16 px in the corner of a
screen, height is legibility and correct letterforms are a detail nobody can
resolve.

### Two things the fill exposed

**The digits fused with the first bar.** With the glyph box ending exactly where
the bars begin, a stretched descender landed on the top bar and the two read as
one mark once downsampled. One nominal pixel is now held back (`GlyphBarGap`);
`The_number_never_touches_the_first_bar` asserts that row is empty and that the
bars are still drawn immediately below it.

**`--` became two solid blocks.** The placeholder is a pair of dashes about 4 px
of ink tall, and filling 46 px with them produced two rectangles that read as
progress bars rather than as "no reading". Caught by regenerating
`docs/screenshots/tray-icons.png`, not by a test — the suite was perfectly happy.

Fixed twice over, deliberately: `MaxGlyphStretch` caps distortion at 1.6 for
anything short and wide, and `DrawPercentage` passes `stretchToFill: false` for
the placeholder outright, because a placeholder has nothing to gain from filling
the box. Two digits need about 1.45, so the cap never touches the case this was
all for.

`A_two_digit_reading_fills_the_height_it_is_given` pins the gain at 90 % of the
box, so a future change to the fit cannot quietly hand the space back.

## Phase 8 — Taskbar widget spike (2026-09-06)

### What was asked

Look at [TrafficMonitor](https://github.com/zhongyang219/TrafficMonitor), which
shows network speed *inside* the Windows taskbar, and use the same strategy to show
the three usage metrics there — something better than a 16 px icon. Once the widget
works the icon becomes the fallback, so strip it to the bare number now.

### How TrafficMonitor does it

Not a widget API. `Shell_TrayWnd` is an ordinary top-level window, so it
`SetParent`s its own dialog into it. On Windows 10 it parents to `ReBarWindow32`
and `MoveWindow`s `MSTaskSwWClass` (the task strip) narrower to make room; on
Windows 11 the strip is a XAML island, so it parents to `Shell_TrayWnd` itself and
overlays, placing itself left of `TrayNotifyWnd`. It re-reads the rects on a 1 s
timer, re-creates itself on the `TaskbarCreated` broadcast, and falls back to a
topmost floating window when `SetParent` fails.

### What was built

- `ITaskbarHost` (Core) — measure / attach / is-attached / move / detach, with
  `nint` handles so Core stays platform-free — and `TaskbarLayout.Compute`, the
  pure placement rule: right-aligned against the tray, full taskbar height,
  DPI-scaled gap, 88 px clock fallback when the tray cannot be measured. One rule
  for Windows 10 and 11, centred and left-aligned taskbars alike, because the
  tray is at the right end in every one of them.
- `WindowsTaskbarHost` (Platform.Windows) — `LibraryImport` over eight user32
  calls. **Only one gotcha:** `GetParent` returns the *owner* for a `WS_POPUP`
  window, which is what an Avalonia window is, so the first run reported the
  re-parenting as failed while the widget was already sitting in the taskbar.
  `GetAncestor(GA_PARENT)` answers the question actually being asked.
- `TaskbarWidgetIndicator` (App) — an `IStatusIndicator` over a chromeless,
  never-activated, transparent `TaskbarWidgetWindow`, re-parented after `Show()`
  and kept in place by a `DispatcherTimer`. `TaskbarWidgetViewModel` reuses
  `UsageBarViewModel` three times, so the widget cannot disagree with the popup
  about formatting or about unknown-is-a-dash. Selected by `--taskbar`; the
  controller does not know which indicator it got.
- `IStatusIndicator.SetThreshold` replaces `SetBarStyle`: the widget shows all
  three metrics and has to judge the two the mode does not cover.

### Result

Works first time on Windows 11 build 26200 at 175 %. The card sits between the
pinned apps and the tray chevron, the transparent corners composite correctly
(Avalonia's `Transparent` hint survives being a child of the taskbar), left click
opens the popup above the widget and right click opens the menu above it. Both
screenshots are in `docs/screenshots/`.

**The contrast problem the tray icon fought for a week does not exist here.**
The widget never draws text on the taskbar. It draws on the theme's own OSD
surface, whose text colour the catalogue has already checked, so it is themed
where the icon could not be — and the popup's transparency setting applies to it
for free.

### The icon

`TrayIconRenderer` lost the three 2 px bars, the small `%`, `TrayBarStyle`, and
about 200 lines of fitting arithmetic that existed to keep a stretched "9" off
the first bar. The number now has the whole 64 px box. Eleven pixel tests that
pinned bar geometry went with them; the two that measure the number's fill were
re-pointed at the full box and still pass at their old thresholds.

### Not done, and known

Explorer restart re-attachment is coded but not exercised; DPI change while
attached is not handled; Windows 10 and secondary taskbars untested; vertical
taskbars refused. The setting to switch indicators comes once those are closed —
see `PLAN.md` §8.2–8.3.

### 8.3 — the setting, the same day

`--taskbar` lasted about an hour. Two settings replace it:

- `AppSettings.Indicator` — `TaskbarWidget` (default) or `TrayIcon`. Offered in
  Config → Display only where `ITaskbarHost.IsSupported`; elsewhere the choice is
  hidden and the factory returns the icon whatever the file says. The controller
  now owns a `Func<IndicatorKind, IStatusIndicator>` instead of a fixed indicator:
  it builds the icon in the constructor (the only kind that needs no settings),
  swaps to the configured kind in `StartAsync` before `Show`, and on Save disposes
  one and creates the other — dispose first, so the user reads it as "switched"
  rather than "doubled". No restart.
- `AppSettings.ShowFableInWidget` — default **false**. Most plans reach the
  session or weekly limit long before the Fable one, and the widget is a third
  narrower without it. The popup and the report always show all three.

`IStatusIndicator.SetThreshold(double)` became `Configure(IndicatorOptions)` so
the second setting had somewhere to travel without a second method. 17 new tests:
settings defaults and normalisation, and the widget view model's threshold
re-evaluation, Fable toggle, stale handling and the three empty states.

### Blending into the taskbar

`AppSettings.WidgetFollowsSystem` (default off). The card goes: transparent
background, no border, and text in the taskbar's own colour - white on a dark
taskbar, near-black on a light one, from the same `ITrayThemeProvider` signal the
icon uses, so the two can never disagree about what reads on this taskbar. The
inks live in `TaskbarInk`, which writes three `Widget.*` brushes into the widget
window's resources on every render; the `.system` styles bind them, so no colour
literal reaches a view or a style. The alert red stays the theme's on purpose -
it is a signal, and a signal that changed with the taskbar would be one less
thing to recognise. Verified visually on the dark taskbar: labels and numbers
match the clock, bars keep their theme fill on a faint ink track.

### Blend on by default, and a real hover card

- `WidgetFollowsSystem` now defaults to **true**. That ran straight into the
  rule on `AppSettings`: the JSON source generator skips initializers, so a
  `bool` whose intended default is `true` reads back `false` from any file that
  lacks the key. Stored inverted as `WidgetUsesThemedCard`, exactly like
  `DisableAutomaticUpdates`; `WidgetFollowsSystem` is `[JsonIgnore]` and computed.
- The widget's tooltip was a one-line string that wrapped wherever the tooltip
  felt like it, leaving the last number alone on a second line. It is now a bound
  `TaskbarWidgetTooltip`: a title, the same "last updated / stale" line the popup
  shows, and one row per limit - full name, percentage, reset countdown - through
  three more `UsageBarViewModel`s keyed to the long names. All three limits are
  listed even when the widget hides Fable: the hover is where the detail lives.
  `ToolTip` itself is now styled with the theme's OSD surface so it matches.
- Fixed a doc-comment slip from earlier today: `IndicatorKind` had been inserted
  between `PollingOptions` and its own summary.
- The widget's context menu drops the **Show ▸** submenu. It picks the one metric
  the tray icon draws, and the widget draws them all, so it changed nothing
  visible there. The setting survives and applies again on switching to the icon.
- The hover card's three rows share column widths (`Grid.IsSharedSizeScope` +
  `SharedSizeGroup`) so "resets with the weekly limit" cannot push its own
  row's percentage out of line. Verified with a headless render.
- Hover card placement: `TopEdgeAlignedRight` with a -10 layout-unit vertical
  offset, so it sits above the widget with their right edges aligned and a gap
  that scales with the screen. The default was pointer-relative with a 20-unit
  drop, which put it wherever the mouse stopped and touching the taskbar.
- Hover card, take two: Avalonia's ToolTip stopped appearing at all once given a
  fixed placement, and with pointer placement it ignored offsets - the widget
  window is a child of the taskbar, and the tooltip service positions relative
  to a window whose coordinates Avalonia does not model there. Replaced by
  `TaskbarHoverWindow`, a window of our own (never activated, topmost, borderless)
  shown 400 ms after the pointer enters the widget and hidden when it leaves or
  clicks. Placed in physical pixels from the taskbar host's own numbers - taskbar
  origin plus the widget's slot - right edges aligned, 10 layout units above.

## Velocity alert (2026-09-06)

The user asked to be warned when usage climbs fast, not just when it is high. A
high number you already see; a fast *rate* is the thing that catches you out mid
task.

- `VelocityRule` (Core): "too fast" is not a fixed rate. It projects the pace
  measured over the recent samples against the window's reset - if usage would
  hit 100 % before the window resets, that is the alert. Two guards keep it quiet:
  the samples must span at least 4 minutes (one long request between two polls is
  not a trend), and the rate must clear 5 %/h (a window already near full "runs
  out before reset" at any positive rate, which is not news). `UsageHistory` keeps
  a 30-minute window of fresh samples and wipes itself on a reset. 11 tests.
- `AppSettings.VelocityAlerts` (default on, stored inverted as
  `DisableVelocityAlerts`). Config -> Behaviour.
- `IStatusIndicator.ShowNotice(text, duration)`: default no-op. The taskbar widget
  opens its hover card of its own accord with a red warning at the foot and takes
  it down after 8 s (unless the pointer is on the widget). The tray icon has no
  surface for it, so there the warning reaches the user only as the details banner.
- The controller (`TrackVelocity`) feeds each fresh reading into per-window
  histories, evaluates session and week, keeps the one that runs out soonest, and
  sets a persistent banner in the details popup plus a once-per-15-minutes flash
  on the indicator. `DetailsViewModel.VelocityText` / `HasVelocityAlert` and
  `TaskbarWidgetViewModel.NoticeText` / `HasNotice` carry it to the views.
